# HERMES EXTRACTOR PIPELINE

## 📱 Hermes APK API Extractor & Diff Engine

Автоматизированный конвейер для реверс-инжиниринга, статического анализа и отслеживания изменений (Diff) сетевого слоя в
мобильных приложениях на базе React Native (движок Meta Hermes, версии байт-кода 90–98+).

## 🚀 Основные возможности

* Zero-Setup (Docker): Не требует локальной установки Python, Java, Rust/Cargo или системных зависимостей Linux.
* Hermes Decompilation: На лету извлекает и декомпилирует бинарные JavaScript-бандлы (`index.android.bundle`) из
  структуры
  APK.
* Smart Extraction: Автоматически вычищает маскировочные обратные слеши (\\), дублирующиеся косые черты (//), кавычки и
  системный XML-мусор Android/Google, собирая только чистые эндпоинты по маске `api/`.
* Diff Engine: При наличии двух и более исходных APK-файлов автоматически генерирует наглядную аналитическую
  Markdown-таблицу эволюции сетевого слоя между версиями.

## 📁 Структура папок на хост-машине

Перед запуском контейнера создайте на своем компьютере две директории:

* `/input` — папка для загрузки исследуемых .apk файлов (одного или нескольких).
* `/output` — папка, куда контейнер сложит готовые текстовые логи и финальную таблицу сравнения.

------------------------------

## 🛠️ Инструкция по сборке и запуску

### 1. Сборка Docker-образа

Выполните команду сборки в терминале (запускается один раз из папки с `Dockerfile` и `pipeline.sh`):

```shell
docker build -t hermes-extractor .
```

### 2. Запуск конвейера анализа

Закиньте необходимые APK-файлы в вашу локальную папку `/input` и запустите контейнер одной командой.

```shell
docker run --rm -v "${PWD}/input:/input" -v "${PWD}/output:/output" hermes-extractor
```

### Или 2 в 1

```shell
docker build -t hermes-extractor .
docker run --rm -v "${PWD}/input:/input" -v "${PWD}/output:/output" hermes-extractor
```

## 🧩 Поддержка ручных переопределений (overrides.json)

Конвейер поддерживает механизм **ручного переопределения данных**, позволяющий уточнять или исправлять автоматически извлечённую информацию из Hermes‑декомпиляции.

Это особенно полезно, когда:

- тело запроса формируется динамически и не может быть восстановлено автоматически;
- метод запроса (GET/POST) определяется не по URL, а по контексту вызова;
- нужно вручную добавить или удалить параметры тела;
- необходимо задать корректное служебное имя эндпоинта;
- требуется зафиксировать реальные поля, найденные при ручном анализе JS‑кода или сниффинге трафика.

### 📌 Где хранится файл переопределений

Создайте файл:

```
/output/overrides.json
```

Он автоматически подхватывается конвейером при каждом запуске.

### 📌 Что можно переопределить

Для любого эндпоинта можно вручную задать:

- `method` — HTTP‑метод (`GET` или `POST`)
- `name` — служебное имя эндпоинта
- `body_fields` — список полей тела запроса
- `query_fields` — список query‑параметров
- `notes` — произвольный комментарий (для документации)

### 📌 Приоритет данных

1. **Ручные данные всегда имеют приоритет** над автоматически извлечёнными.
2. Если параметр не указан вручную — используется автоматически найденный.
3. Если эндпоинт отсутствует в автоматическом анализе — он будет создан полностью из `overrides.json`.

### 📌 Пример файла `/output/overrides.json`

```json
{
  "api/mobile/orders/1010/app-rating": {
    "method": "POST",
    "name": "ratingAppManual",
    "body_fields": [
      "orderNum",
      "rating",
      "authToken"
    ],
    "query_fields": [
      "guid"
    ],
    "notes": "Реальное тело запроса найдено вручную при анализе JS"
  },

  "epz/api/priz/mobile/search": {
    "method": "POST",
    "body_fields": [
      "orderNum",
      "pageNumber",
      "limit"
    ],
    "notes": "Тело запроса подтверждено сниффингом трафика"
  }
}
```

### 📌 Как это отображается в итоговой спецификации

В файле:

```
/output/spec/FULL_API_SPECIFICATION.txt
```

для эндпоинтов с ручными данными будет указано:

```
🔹 Источник данных   : manual override
```

А тело запроса будет ссылаться на файл:

```
spec/bodies/<endpoint>.json
```

### 📌 Как это отображается в сравнительной таблице

В файле:

```
/output/spec/API_VERSIONS_DIFF.md
```

в разделе полной спецификации эндпоинта будет:

```
### Источник данных: manual override
```

## 📊 Результаты работы

После завершения работы контейнера в вашей папке `/output` появятся следующие файлы:

1. `Индивидуальные логи версий (.txt)` — названные точно так же, как исходные APK. Содержат чистый, отсортированный по
   алфавиту список уникальных путей API.
2. `API_VERSIONS_DIFF.md` — общая сравнительная матрица (создается автоматически, если в `/input` было 2+ файла).

### Пример генерируемой Diff-таблицы:

| Название эндпоинта шлюза API            | 13.3.2-5 | 14.3.1 | 16.1.3.1-8 |
|-----------------------------------------|----------|--------|------------|
| api/mobile/chat/mobileChat?             | ➕        | ➕      | ➕          |
| api/mobile/news/{id}/detail/            | ❌        | ➕      | ➕          |
| epz/api/priz-fz223/mobile/card/lot-info | ➕        | ➕      | ➕          |
| mess/profiles-api/api/profiles          | ❌        | ❌      | ➕          |

* ➕ — эндпоинт присутствует в данной версии приложения.
* ❌ — эндпоинт отсутствует (был удален или еще не внедрен).

## ⚠️ Системные требования

* Установленный Docker Desktop (с включенным бэкендом WSL 2, если запуск производится на Windows).
* Корректные права на чтение/запись для монтируемых папок `/input` и `/output`.
